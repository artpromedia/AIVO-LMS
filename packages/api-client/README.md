# `@aivo/api-client`

Typed bindings for AIVO backend services, generated from each service's
Fastify-emitted OpenAPI document. This package contains **types only** —
it deliberately ships no runtime client. Web (`apps/web`) and mobile
(`apps/mobile`) keep their existing `apiFetch` helpers and import
request/response shapes from here.

## Phase 5 staging

- **5.0** — package skeleton, dump script, generator, CI drift check.
- **5.1** — every service in `SERVICES` exports `buildApp()` and is
  dumped to `openapi/*.json`. Specs at this stage have empty / unknown
  shapes for most non-health routes; that is expected.
- **5.2** — per-route Fastify JSON Schemas (`body` / `querystring` /
  `params` / `response`) on every public route, plus `tags` and a
  stable `operationId`. `learning-svc` is the reference; see
  [`services/learning-svc/src/routes/schemas.ts`](../../services/learning-svc/src/routes/schemas.ts)
  for the canonical pattern.
- **5.last** — flip the drift workflow's `continue-on-error` to `false`
  and the `no-restricted-syntax` interface guard in
  `apps/{web,mobile}/eslint.config.mjs` from `warn` to `error` in the
  same commit, after every service finishes 5.2.

## Schema authoring pattern (5.2)

Schemas live next to the routes that use them (`routes/schemas.ts`) and
are imported into the route registration:

```ts
// routes/schemas.ts
const errorResponse = {
  type: "object",
  required: ["error"],
  additionalProperties: true,
  properties: { error: { type: "string" } },
} as const;

export const createFooSchema = {
  tags: ["Foo"], // groups the swagger UI surface
  operationId: "createFoo", // names the generated `operations` entry
  summary: "Create a foo", // becomes the JSDoc on `paths[...]`
  body: {
    type: "object",
    required: ["name"],
    additionalProperties: true,
    properties: { name: { type: "string" } },
  },
  response: {
    200: {
      type: "object",
      required: ["id", "name"],
      additionalProperties: true, // do NOT strip extra fields
      properties: {
        id: { type: "string" },
        name: { type: "string" },
      },
    },
    400: errorResponse,
  },
} as const;
```

```ts
// routes/foo.ts
import { createFooSchema } from "./schemas.js";

app.post("/api/foo", { schema: createFooSchema }, async (request, reply) => {
  /* ... */
});
```

Conventions:

1. **Always set `additionalProperties: true` on response objects.**
   Fastify's response serializer (`fast-json-stringify`) drops
   undeclared fields by default. With drizzle row spreads or
   sessionData blobs in the response, that silently breaks callers.
   Declare the _minimum_ fields you want documented in `properties`,
   then leave `additionalProperties: true` to let the rest flow
   through.
2. **Tag every public route.** Pick one tag per service surface (e.g.
   `Learning`, `Identity`, `Tutor`) so the swagger UI groups things.
3. **Set `operationId` on every route.** This is what the generated
   client uses as the type alias name; without it, openapi-typescript
   falls back to a verbose path-derived name.
4. **Reuse error envelopes.** Define one `errorResponse` const at the
   top of the schemas file and reference it from every non-2xx code.
   If a route adds diagnostic fields (e.g. `qualityScore`), spread the
   envelope: `{ ...errorResponse, properties: { ...errorResponse.properties, qualityScore: { type: "number" } } }`.
5. **Use `as const`.** Keeps Fastify's TypeProvider machinery happy if
   we adopt one later, and prevents accidental mutation.

## Layout

```
packages/api-client/
├── openapi/                # committed JSON dumps, one per service
│   ├── identity-svc.json
│   ├── learning-svc.json
│   └── …
├── src/
│   ├── index.ts            # auto-generated barrel of namespaces
│   ├── identity-svc.ts     # auto-generated by openapi-typescript
│   ├── learning-svc.ts
│   └── …
└── README.md
```

Both `openapi/<svc>.json` and `src/<svc>.ts` are generated and
committed. CI (`.github/workflows/api-client-drift.yml`) regenerates
them on every PR and fails if the working tree differs from what was
committed, so the spec on disk is always in sync with the route schemas
in the corresponding service.

## Pipeline

```
service Fastify routes (with @fastify/swagger schemas)
        │
        ▼  pnpm api:dump
packages/api-client/openapi/<svc>.json
        │
        ▼  pnpm api:generate     (runs api:dump first)
packages/api-client/src/<svc>.d.ts
        │
        ▼  callers import { paths, components }
apps/web, apps/mobile
```

Root scripts:

| Command             | Purpose                                                         |
| ------------------- | --------------------------------------------------------------- |
| `pnpm api:dump`     | Boot each registered service in-process, write `openapi/*.json` |
| `pnpm api:generate` | Run `api:dump`, then `openapi-typescript` per spec              |
| `pnpm api:check`    | Run `api:generate`, fail if `git diff` is non-empty             |

`api:check` is the CI gate.

## Consuming the types

Once a service has been onboarded:

```ts
import type { paths } from "@aivo/api-client/identity-svc";

type LoginBody = paths["/api/auth/login"]["post"]["requestBody"]["content"]["application/json"];
type LoginRes = paths["/api/auth/login"]["post"]["responses"]["200"]["content"]["application/json"];

const res = await apiFetch("/api/auth/login", { method: "POST", body: JSON.stringify(body) });
const data: LoginRes = await res.json();
```

No runtime is shipped: `apiFetch` continues to live in each app.

## Onboarding a new service (5.1+)

1. **Make the service dumpable.** Refactor `services/<svc>/src/index.ts`
   so the Fastify app is built in an exported `buildApp()` function (see
   `services/identity-svc/src/index.ts` for the reference shape). The
   `start()`/`listen()` call must not happen at module top level.
2. **Register `@fastify/swagger` + `@fastify/swagger-ui`** if missing.
3. **Add per-route schemas** (`schema: { body, params, querystring,
response }`) following the pattern documented above. Without these,
   the dump emits an empty path object. `learning-svc` is the canonical
   reference — copy `services/learning-svc/src/routes/schemas.ts` as a
   starting point.
4. **Register the service** in `scripts/dump-openapi.mjs` by appending
   an entry to `SERVICES`.
5. Run `pnpm api:generate` and commit the new `openapi/<svc>.json` and
   `src/<svc>.ts`.
6. Migrate callers off any inline `interface XYZResponse { ... }`
   declarations in `apps/web` and `apps/mobile` onto the generated
   `paths` types. The ESLint guard
   (`no-restricted-syntax` ban on `interface *Response` in
   `apps/web/eslint.config.mjs` and `apps/mobile/eslint.config.mjs`)
   catches new offenders. Existing offenders are explicitly
   allowlisted in those configs and should be removed as their source
   service finishes 5.2.

## Risks / things that bit us

- `@fastify/swagger` will silently emit `{}` for routes without a
  `schema` block. The generated client will compile but be useless.
  Always add at least a `response` schema.
- Strict response validation can reject responses that include fields
  not declared in the schema. Land schemas with the default loose
  response mode first and tighten later.
- Booting a service for the dump pulls in real plugins (DB, MFA key,
  rate-limit). The dump script sets stub env vars (`DATABASE_URL`,
  `MFA_AT_REST_KEY`, `NODE_ENV=test`) so `buildApp()` succeeds without
  hitting Postgres. Service refactors should keep DB queries lazy
  (driver-level, not at boot).
