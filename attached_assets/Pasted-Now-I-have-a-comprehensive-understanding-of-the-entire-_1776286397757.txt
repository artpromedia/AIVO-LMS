## 1. Executive Summary

### 1.1 Purpose

This PRD defines the complete requirements for evolving the AIVO Platform Super Admin Panel from its current v1 state — a functional but limited administrative dashboard — into a robust, enterprise-grade platform control center. The Super Admin Panel is the single pane of glass through which `PLATFORM_ADMIN` users operate, monitor, and govern the entire AIVO ecosystem across 15 microservices, 13 user roles, 14 AI tutors, multi-tenant architecture, and global compliance requirements.

### 1.2 Current State Assessment

The existing admin panel at `/dashboard/admin/` has **10 sub-pages** served from a well-structured Next.js layout:

| Page | Route | Current State | Gap Assessment |
|---|---|---|---|
| **Overview** | `/dashboard/admin` | ✅ Functional — stat cards, role chart, service health, recent users, 30-day uptime | Missing: real-time websocket updates, global search, activity feed timeline |
| **Users & Roles** | `/dashboard/admin/users` | ✅ Functional — CRUD, role filter, search, pagination, impersonation, create modal | Missing: edit/delete user, role change, password reset, bulk ops, export, detailed user profile view |
| **Learners** | `/dashboard/admin/learners` | ✅ Functional — list with filtering by functioning level, pagination | Missing: learner detail drilldown, brain state viewer, parent linkage, assessment history |
| **Tenants & Districts** | `/dashboard/admin/tenants` | ✅ Functional — list with type filter, create district form | Missing: tenant detail view, edit, school management under districts, license management, usage dashboard per tenant |
| **Services & Health** | `/dashboard/admin/services` | ✅ Functional — 15 services listed with real-time polling (15s), incidents, uptime | Missing: service logs viewer, restart capability, dependency graph, alerting config |
| **Analytics & Research** | `/dashboard/admin/analytics` | ✅ Functional — engagement metrics, mastery by subject, cohort breakdown, export | Missing: time-range selectors, charts/graphs, trend analysis, comparison tools, scheduled reports |

| **Compliance & Audit** | `/dashboard/admin/compliance` | ⚠️ Partially static — compliance checks are **hardcoded arrays** not from API, audit log is **mock data** | Missing: real audit log API integration, data request workflow, compliance scan automation, consent management CRUD |
| **Platform Settings** | `/dashboard/admin/settings` | ✅ Functional — feature flags, system limits, save to API | Missing: environment management, email template config, notification settings, webhook management, API key management |

### 1.3 Backend API Assessment

Admin operations are split across **two backend services**:

1. **`identity-svc` (:3001)** — `services/identity-svc/src/routes/admin.ts` (311 lines)
   - `GET /api/admin/stats` — dashboard stats
   - `GET /api/admin/users` — user listing
   - `GET /api/admin/tenants` — tenant listing
   - `GET /api/admin/learners` — learner listing
   - `POST /api/admin/create-team-member` — create user with any of 13 roles
   - `POST /api/admin/create-district` — create district with admin account
   - Auth guards: `requireAdmin` (PLATFORM_ADMIN + DISTRICT_ADMIN), `requirePlatformAdmin` (PLATFORM_ADMIN only)

2. **`admin-svc` (:3013)** — `services/admin-svc/src/routes/platform.ts` (77 lines)
   - `GET /api/admin-svc/stats` — duplicate stats endpoint
   - `GET /api/admin-svc/users` — duplicate user listing
   - `GET /api/admin-svc/learners` — duplicate learner listing
   - `GET /api/admin-svc/tenants` — duplicate tenant listing
   - `GET /api/admin-svc/config` — feature flags and limits
   - `PUT /api/admin-svc/config` — update config (stub — returns input without persisting)

**Key Backend Gap:** The `admin-svc` largely duplicates `identity-svc` admin routes. The config PUT endpoint is a stub. No audit logging, no user update/delete, no tenant update, no real-time events, no data export endpoints.

## 3. User Personas & Permissions

### 3.1 Primary User: Platform Super Admin (`PLATFORM_ADMIN`)

- **Who:** AIVO founding team, CTO, Head of Engineering, Head of Operations
- **Access Level:** Full read/write across all platform entities, all tenants, all services
- **Daily Tasks:** Monitor service health, review new signups, manage districts, review compliance, check revenue, review AI safety, impersonate users for support
- **Capabilities:** Everything — no restrictions

### 3.2 Secondary User: District Admin (`DISTRICT_ADMIN`)

- **Who:** District IT administrators, school principals
- **Access Level:** Read/write within their tenant only
- **Admin Panel Access:** Should **NOT** see the Super Admin panel — they have their own `/dashboard/district` panel. However, some admin APIs serve both roles (stats, users within tenant scope). The PRD scope is exclusively the Super Admin experience.

### 5.5 Module: Real Audit Logging System

**Routes:** `/dashboard/admin/compliance/audit-log` (new) + update `/dashboard/admin/compliance`

#### 5.5.1 Database Schema

```sql
CREATE TABLE admin_audit_log (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  action VARCHAR(100) NOT NULL,           -- e.g. USER_CREATED, ROLE_CHANGED, CONFIG_UPDATED
  actor_id UUID NOT NULL REFERENCES users(id),
  actor_email VARCHAR(255) NOT NULL,
  actor_role VARCHAR(50) NOT NULL,
  resource_type VARCHAR(50) NOT NULL,     -- User, Learner, Tenant, Config, Session
  resource_id VARCHAR(255),
  details JSONB,                          -- structured payload of what changed
  ip_address INET,
  user_agent TEXT,
  tenant_id UUID REFERENCES tenants(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_audit_log_actor ON admin_audit_log(actor_id);
CREATE INDEX idx_audit_log_action ON admin_audit_log(action);
CREATE INDEX idx_audit_log_resource ON admin_audit_log(resource_type, resource_id);
CREATE INDEX idx_audit_log_created ON admin_audit_log(created_at DESC);
```

#### 5.5.2 Actions to Log

Every admin write operation must create an audit entry:

| Action Code | Trigger | Details Payload |
|---|---|---|
| `USER_CREATED` | `POST /api/admin/create-team-member` | `{ userId, name, email, role, tenantId }` |
| `USER_UPDATED` | `PUT /api/admin/users/:id` | `{ userId, changes: { before, after } }` |
| `USER_DEACTIVATED` | `DELETE /api/admin/users/:id` | `{ userId, name, email }` |
| `USER_PASSWORD_RESET` | `POST /api/admin/users/:id/reset-password` | `{ userId, email }` |
| `ROLE_CHANGED` | `PUT /api/admin/users/:id` (role field changed) | `{ userId, oldRole, newRole }` |
| `IMPERSONATION_STARTED` | Impersonate action | `{ targetUserId, targetRole }` |
| `IMPERSONATION_ENDED` | Return to admin | `{ targetUserId, duration }` |
| `TENANT_CREATED` | `POST /api/admin/create-district` | `{ tenantId, name, type }` |
| `TENANT_UPDATED` | `PUT /api/admin/tenants/:id` | `{ tenantId, changes }` |
| `TENANT_SUSPENDED` | Suspend action | `{ tenantId, reason }` |
| `CONFIG_UPDATED` | `PUT /api/admin-svc/config` | `{ changes: { flagName: { before, after } } }` |
| `INCIDENT_CREATED` | `POST /api/status/incidents` | `{ incidentId, title, severity }` |
| `INCIDENT_RESOLVED` | `PUT /api/status/incidents/:id` | `{ incidentId, resolvedAt }` |
| `BRAIN_RESET` | `POST /api/admin/learners/:id/reset-brain` | `{ learnerId, learnerName, reason }` |
| `DATA_EXPORT` | `GET /api/research/export/anonymized` | `{ format, scope }` |
| `DATA_REQUEST_PROCESSED` | GDPR/CCPA request workflow | `{ requestType, subjectId }` |
| `LOGIN` | Admin login | `{ ip, userAgent }` |
| `LOGIN_FAILED` | Failed admin login attempt | `{ email, ip, reason }` |

## 6. Backend API Consolidation Strategy

### 6.1 Problem

Admin routes are currently split between `identity-svc` and `admin-svc` with significant duplication. Both have `/api/admin/stats`, user listing, learner listing, and tenant listing.

### 6.2 Recommendation

**Consolidate all admin API endpoints into `admin-svc`** as the single entry point. `admin-svc` should make internal service calls to `identity-svc`, `billing-svc`, `engagement-svc`, etc. to aggregate data.

| Current | Target |
|---|---|
| `identity-svc: GET /api/admin/stats` | Deprecate → `admin-svc: GET /api/admin-svc/stats` (calls identity-svc internally) |
| `identity-svc: GET /api/admin/users` | Deprecate → `admin-svc: GET /api/admin-svc/users` |
| `identity-svc: POST /api/admin/create-team-member` | Keep (identity-svc owns user creation) |
| `identity-svc: POST /api/admin/create-district` | Keep (identity-svc owns tenant creation) |
| `admin-svc: PUT /api/admin-svc/config` | Fix — implement real persistence |
| New audit-log, billing, moderation, compliance APIs | Add to `admin-svc` |

**During migration:** Support both old and new API paths. Frontend switches to admin-svc paths. Mark identity-svc admin routes as deprecated with sunset header.

## 7. Non-Functional Requirements

### 7.1 Performance

| Requirement | Target |
|---|---|
| Admin page first contentful paint | < 2s |
| API response time (list endpoints) | < 500ms for up to 200 records |
| API response time (detail endpoints) | < 300ms |
| Real-time update latency (WebSocket) | < 2s from event to UI update |
| Service health poll interval | 15s (existing, keep) |
| Search results | < 1s for command palette |

### 7.2 Security

| Requirement | Implementation |
|---|---|
| All admin APIs require valid JWT | ✅ Existing `requireAdmin` / `requirePlatformAdmin` middleware |
| Step-up authentication for destructive actions | New: user deletion, tenant deletion, brain reset require MFA re-verification |
| Rate limiting on admin APIs | 100 req/min per admin (existing config) |
| Audit logging is immutable | Append-only table, no UPDATE/DELETE on `admin_audit_log` |
| IP allowlisting (optional) | P2: configurable IP whitelist for admin access |
| Session timeout | Admin sessions expire after 4 hours of inactivity |

### 7.3 Accessibility

| Requirement | Standard |
|---|---|
| All admin pages pass axe-core | WCAG 2.1 AA, zero violations |
| Keyboard navigation | All admin actions achievable via keyboard only |
| Screen reader compatibility | All data tables have proper `<th>` headers, `<caption>`, `role` attributes |

| Focus management | Modals trap focus, dialogs auto-focus first field |

```sql

CREATE TABLE webhooks (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  url VARCHAR(2048) NOT NULL,
  events VARCHAR(100)[] NOT NULL,        -- e.g. {"user.created", "brain.updated"}
  secret VARCHAR(255) NOT NULL,          -- HMAC signing secret
  active BOOLEAN DEFAULT TRUE,
  tenant_id UUID REFERENCES tenants(id), -- null = platform-wide
  created_by UUID REFERENCES users(id),
  last_delivery_at TIMESTAMPTZ,
  last_delivery_status VARCHAR(20),
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE webhook_deliveries (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  webhook_id UUID NOT NULL REFERENCES webhooks(id),
  event VARCHAR(100) NOT NULL,
  payload JSONB NOT NULL,
  response_status INT,
  response_body TEXT,
  delivered_at TIMESTAMPTZ DEFAULT NOW()
);

-- API Keys (Section 5.9.4)
CREATE TABLE api_keys (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  key_hash VARCHAR(255) NOT NULL,        -- bcrypt hash of the key
  key_prefix VARCHAR(10) NOT NULL,       -- first 8 chars for identification
  name VARCHAR(255) NOT NULL,
  scopes VARCHAR(50)[] NOT NULL,         -- e.g. {"read:users", "read:learners"}
  tenant_id UUID REFERENCES tenants(id),
  created_by UUID REFERENCES users(id),
  expires_at TIMESTAMPTZ,
  last_used_at TIMESTAMPTZ,
  revoked_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Data requests (Section 5.8.2)
CREATE TABLE data_requests (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  type VARCHAR(50) NOT NULL,             -- "access", "deletion", "export"

  subject_id UUID REFERENCES users(id),
  subject_email VARCHAR(255),
  requester_id UUID REFERENCES users(id),
  notes TEXT,
  admin_notes TEXT,
  sla_deadline TIMESTAMPTZ,
  completed_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- AI usage tracking (Section 5.7.1)
CREATE TABLE ai_usage_log (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  provider VARCHAR(50) NOT NULL,         -- "anthropic", "google", "openai"

  input_tokens INT NOT NULL,
  output_tokens INT NOT NULL,
  latency_ms INT NOT NULL,
  estimated_cost_usd DECIMAL(10, 6),
  learner_id UUID,
  tutor_key VARCHAR(50),
  session_id UUID,

CREATE INDEX idx_ai_usage_created ON ai_usage_log(created_at DESC);
CREATE INDEX idx_ai_usage_provider ON ai_usage_log(provider, created_at DESC);

-- Content moderation (Section 5.7.3)
CREATE TABLE content_moderation_queue (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  content TEXT NOT NULL,
  content_type VARCHAR(50) NOT NULL,     -- "tutor_response", "generated_problem", "explanation"
  flag_reason VARCHAR(100) NOT NULL,     -- "bias", "safety", "quality", "off_topic"
  flag_confidence DECIMAL(3, 2),
  tutor_key VARCHAR(50),
  provider VARCHAR(50),
  learner_id UUID,                       -- anonymized in admin view
  status VARCHAR(50) NOT NULL DEFAULT 'pending',
  reviewer_id UUID REFERENCES users(id),
  reviewer_action VARCHAR(50),           -- "approved", "confirmed", "escalated"
  reviewed_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Platform config versioning (Section 5.9.1)
CREATE TABLE platform_config (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  config JSONB NOT NULL,
  changed_by UUID REFERENCES users(id),
  change_description TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

## 11. Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| API consolidation breaks existing admin flows | Medium | High | Feature-flag new APIs, keep old paths during migration, run both in parallel |
| Stripe billing API integration complexity | Medium | Medium | Start with read-only Stripe data, add write operations later |
| Audit log table grows very large | High | Low | Implement partition by month, add retention policy (2 years), consider archival to cold storage |
| Prompt Playground could be abused for free LLM access | Low | Medium | Rate limit playground to 50 requests/day per admin, log all usage |
| Real compliance checks may reveal actual non-compliance | Medium | High | Run automated checks in staging first, create remediation plan before showing in production |
| Performance degradation from detail page aggregation queries | Medium | Medium | Use database views or materialized views for heavy aggregation queries, add Redis caching layer |
