### 1.3 The #1 Systemic Problem: No Tenant Data Isolation

**This is a launch-blocking security vulnerability.** Every API call from the district dashboard hits platform-wide admin endpoints:

| Frontend Call | Backend Endpoint | What It Returns | What It Should Return |
|---|---|---|---|
| `GET /api/admin/stats` | `identity-svc` → queries all users/learners/tenants globally | Platform-wide totals | Only this district's users/learners |
| `GET /api/admin/learners` | `identity-svc` → queries all learners globally | ALL learners on the platform | Only learners within this district's tenant |
| `GET /api/admin/users?role=TEACHER` | `identity-svc` → queries all users by role globally | ALL teachers platform-wide | Only teachers assigned to this district |
| `GET /api/admin/tenants` | `identity-svc` → queries all tenants globally | ALL tenants on the platform | Only this district's tenant and its child schools |

The `requireAdmin` middleware in `identity-svc/src/routes/admin.ts` allows both `PLATFORM_ADMIN` and `DISTRICT_ADMIN` through, but **never applies a tenant filter** (`WHERE tenantId = ?`). The frontend does some client-side filtering (e.g., schools page filters `all.filter(t => t.id === user.tenantId)`), but the data has already been sent over the network.

**This must be the first thing fixed before any feature work.**

### 5.1 Module: Tenant-Scoped Backend API Layer (P0 — MUST be first)

#### 5.1.1 New District-Scoped API Endpoints

Create a new file: `services/identity-svc/src/routes/district.ts`

All endpoints use a new `requireDistrictAdmin` middleware that:
1. Verifies JWT
2. Confirms role is `DISTRICT_ADMIN` (or `PLATFORM_ADMIN` with `?tenantId=` override)
3. Extracts `tenantId` from the JWT payload
4. Automatically applies `WHERE tenantId = ?` to all queries

```typescript
// New middleware
async function requireDistrictAdmin(req, reply) {
  const payload = await verifyJWT(token);
  if (!["DISTRICT_ADMIN", "PLATFORM_ADMIN"].includes(payload.role)) {
    return reply.status(403).send({ error: "District admin access required" });
  }
  // For PLATFORM_ADMIN, allow optional tenantId query param to scope
  req.tenantId = payload.role === "PLATFORM_ADMIN" 
    ? (req.query.tenantId || payload.tenantId)
    : payload.tenantId;
  
  if (!req.tenantId) {
    return reply.status(400).send({ error: "No tenant context" });
  }
  req.user = payload;
}
```

## 7. Non-Functional Requirements

### 7.1 Performance

| Requirement | Target |
|---|---|
| Dashboard first contentful paint | < 2s |
| Learner list with 500 records | < 1s (server-side paginated) |
| Analytics charts render | < 3s with 1000+ learner dataset |
| Report PDF generation | < 15s for district-wide report |
| Search results | < 500ms |

### 7.2 Security

| Requirement | Implementation |
|---|---|
| Tenant data isolation | Server-side `WHERE tenantId = ?` on EVERY query — zero client-side filtering |
| JWT tenant claim validation | Backend verifies `tenantId` in JWT matches the requested data scope |
| FERPA compliance | All data exports are de-identifiable; student PII protected |
| COPPA compliance | District admin cannot see parent-child private conversations or brain review content |
| Session management | District admin sessions expire after 8 hours of inactivity |
| Rate limiting | 60 req/min per district admin |
| Audit logging | All district admin write actions logged to `district_activity_log` |

### 7.3 Accessibility

| Requirement | Standard |
|---|---|
| WCAG 2.1 AA compliance | All pages |
| Keyboard navigation | Complete — all actions, modals, tabs, filters |
| Screen reader support | Proper headings hierarchy, table captions, ARIA labels |
| Color contrast | 4.5:1 minimum for text, 3:1 for large text and UI components |
| Focus management | Modal focus trap, skip links (already exists in layout) |
| Reduced motion | Respect `prefers-reduced-motion` for all animations |
| Existing compliance | Maintain `SkipLink`, `aria-label`, `aria-current`, `role="navigation"` from layout |

### 7.4 Internationalization

| Requirement | Implementation |
|---|---|
| All text uses `next-intl` | ✅ Existing — uses `useTranslations("districtAdmin")` |
| New pages follow same pattern | All new strings added to `districtAdmin` namespace |
| Date/time formatting | Use `next-intl` formatters, respect locale |
| Number formatting | Use `Intl.NumberFormat` for enrollment counts, percentages |

### 7.5 Neurodiverse-Friendly UX

The district panel serves administrators who manage learners with diverse needs. The panel itself should be exemplary:

| Guideline | Implementation |
|---|---|
| Clear visual hierarchy | Consistent heading sizes, predictable layout patterns |
| Minimal cognitive load | Progressive disclosure — summary views first, detail on click |
| Consistent navigation | Same sidebar structure across all pages, breadcrumbs for drill-down |
| Status indicators | Always use both color AND icon/text (never color-alone for status) |
| Data density control | Toggle between summary/detailed views |
| Predictable interactions | Same patterns for tables, filters, modals across all pages |
| Loading states | Skeleton placeholders for all async content (already used consistently) |

## 10. Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Tenant isolation bypass via API manipulation | Low (if implemented correctly) | Critical | Backend-enforced scoping on every query; integration tests; security review |
| Performance with large districts (5000+ learners) | Medium | High | Server-side pagination everywhere; database indexes; materialized views for analytics |
| IEP data sensitivity (PII + medical) | High | Critical | Field-level encryption for disability categories; strict FERPA handling; audit logging |
| SSO configuration complexity | Medium | Medium | Pre-built IdP templates (Azure AD, Google); step-by-step wizard; "Test Connection" before activation |
| Report generation timeout for large datasets | Medium | Medium | Async report generation with progress indicator; pre-computed analytics views |
| Integration sync creates duplicate learners | Medium | High | Deduplication logic in sync handler; merge UI for district admin to resolve conflicts |
| District admins expecting real-time data | Low | Medium | Clear "last updated" timestamps; polling for analytics (not websocket) |

## 13. Glossary

| Term | Definition |
|---|---|
| **Tenant** | Organizational unit in AIVO — for districts, type = `B2B_DISTRICT` |
| **School** | A child entity under a district tenant — represents a physical school building |
| **Classroom** | A grouping within a school — has a teacher, grade level, enrolled learners |
| **IEP** | Individualized Education Program — federal mandate for students with disabilities |
| **Triennial** | Every 3 years, students with IEPs must be re-evaluated |
| **RTI/MTSS** | Response to Intervention / Multi-Tiered System of Supports — framework for identifying and supporting struggling learners |
| **Functioning Level** | AIVO's 5-tier classification: Standard, Supported, Low Verbal, Non-Verbal, Pre-Symbolic |
| **Brain Clone** | AIVO's adaptive learning profile per learner |
| **Caseload** | The set of learners assigned to a specific teacher, therapist, or caregiver |
| **AYP** | Adequate Yearly Progress — state-mandated academic growth metric |
| **SIS** | Student Information System — district's existing student database (PowerSchool, Infinite Campus, etc.) |
| **Roster Sync** | Automatic import of students, teachers, and classes from SIS via integrations (Clever, ClassLink, etc.) |
